# 互換性と実装状況

## 状態の意味

- **実装済み**: 現行 Rust に処理があり、対応テストまたは出力処理を確認できるもの。
- **一部**: 基本形は動くが、従来版の全オプション・派生形を満たさないもの。
- **警告**: 構文を読み飛ばし、警告してコンパイルを続けるもの。効果はない。
- **未実装**: 現行 Rust ではコマンドとして受理しないもの。

今回、実装済み機能のバグとして次をPascal由来の最小ゴールデンテストへ還元しました。

- 音色を現在位置の1 tick前、通常のCCとピッチベンドを`System.ControllerShift`だけ前へ置く。
- バンク付き音色ではCC0、CC32、Program Changeを従来どおりの間隔と順序で出力する。
- `n(note),0 ... n(note),length`形式の和音を最後の正の音長でまとめて出力する。
- 空文字列のメタイベントを、Pascal版と同じ1個の空白として出力する。

残差のうち、未実装機能は上記の個別Issueで追跡します。それ以外は実装済み機能の
イベント時刻・順序・ゲート計算のバグであり、同じ手順で最小化してから修正します。

## 重要な互換性注意点

### トラック番号

現行 Rust はPascal版と同様にトラック0から開始し、新しいトラック n の既定チャンネルは
n（16を上限、トラック0と1はどちらもチャンネル1）です。明示的な`Track 1`より前に書いた
メタイベントやリセットはMTrk 0に残ります。

### 先行指定

未実装の先行指定は警告して無視する場合があります。コンパイル成功だけでは音響互換を保証しません。
特に CC、ピッチベンド、波形、ランダム、時刻予約を使う曲は警告を確認し、Pascal 出力と比較してください。

### TempoChange

従来版は開始値、終了値、期間から複数のテンポイベントを生成します。現行 Rust の `TempoChange` は
単一 BPM だけを受け取る即時 `Tempo` の別名です。従来形式の複数引数は受理せず、推移を必要とする曲では非互換です。

### ストトン表記

ストトン表に、未実装コマンドへ展開される語があります。日本語入力を正常に置換できることと、
置換先コマンドが実装済みであることは別です。

## 仕様追加時の確認手順

1. [従来版の全コマンド表](12-legacy-command-table.md) と該当する `doc/command/*.htm` で書式を確認する。
2. Pascal のディスパッチ先と状態更新を確認する。
3. 最小 MML を Pascal 版で変換し、MIDI バイトまたはイベント列を採取する。
4. Rust に異常系を含む回帰テストを追加する。
5. 本表と該当する詳細章を同時に更新する。

## 乱数について

`Random()`、`.Random`、「曖昧さ」が返す値は、従来版と一致しません。従来版は処理系の乱数
（FPC ビルドと Delphi ビルドでも異なる）を使うため、そもそも一意な基準が存在しないためです。

現行 Rust は crate 内に持つシード付き生成器を使います。同じ入力からは常に同じ出力が得られ、
`System.RandomSeed` で系列を選べます。WASM で追加の乱数源を必要としないのも同じ理由です。
値の並びではなく、範囲と分布が仕様です。

## Cresc / Decresc の括弧形式について

`Cresc`/`Decresc`はExpression（CC11）を推移させる命令で、`=`形式（`Cresc=len,v1,v2`）と
括弧形式（`Cresc(len,v1,v2)`）の2つの書き方があります。従来版にはこの2つで**動作が異なる
バグ**があり、現行 Rust はそれをそのまま再現しています（`cresc_sub`のGetNoteLengthが
括弧内の値リストを消費してしまい、`len`しか読み取れない）。

- `Cresc=len,v1,v2` — 正しく`v1`・`v2`を読み取る。**ストトンの「大きく」「小さく」は
  常にこの形式に展開される**ため、実運用には影響しない。
- `Cresc(len,v1,v2)` — `len`のみ読み取り、`v1`・`v2`は無視されて既定値
  （Crescは40→127、Decrescは127→40）が使われる。`Cresc=(len,v1,v2)`（`=`の後に
  括弧を付けた形）も同じバグの影響を受ける。

`v1`を省略した1引数形式（`Cresc=len,v2`）では、`v1`はCC11に最後に書き込まれた値
（何も書き込まれていなければ0）になります。この値はCresc/Decresc自身だけでなく、
`EP(...)`や`y11,...`など他のCC11書き込み全てで更新されます。

いずれの形式も、書き込み中はトラックの時間ポインタを進めません（推移イベントを
現在位置の前後に書き込むだけで、後続のコマンドは即座に同じ時刻から始まります）。

参照実装: `core/src/compiler/mod.rs`の`Compiler::cresc`、テストは
`core/tests/golden.rs`の`cresc_*`/`decresc_*`。

## PlayFrom / PlayTo について

曲の途中から（または途中までを）演奏用に書き出す機能です。`PlayFrom(time)`が指定した位置
より前のイベントを間引き、生き残ったイベントを`time - fromPos + waitTime`だけ巻き戻します
（`waitTime`は既定192tick — 再構成した状態を書き込む余地）。`PlayTo(time)`はその位置以降を
切り捨てます。全体は`(FromPos>0) or (ToPos>0)`のときだけ動作し、それ以外（例えば
`PlayFrom(1:1:0)`のように0を指定した場合）は完全な無処理です。曲の先頭で「演奏位置」を
書く定番のイディオムはこちらに該当します。

適用はコンパイル全体が終わった後に一括で行われるため、`PlayFrom`をソース中のどこに書いても
結果は変わりません（従来版の`TSmfTrack.ExecutePlayFrom`が保存時に後処理として実行するのと
同じ設計です）。

カット位置をまたいで生き残る音符が違和感なく鳴るよう、カット直前の状態
（コントロールチェンジ・ピッチベンド・音色・テンポ）を復元して書き込み直します。

**簡略化している点**: RPN/NRPNの再構成は未実装です。従来版はカット前のRPN/NRPN関連CC
（データエントリを含む）を専用のイベントとして復元しますが、現行 Rust はこれを行いません
（`.RPN_NRPN`オプション自体は解析しますが効果を持ちません）。また`.SysEx`オプションで
SysExイベントを保持する動作も実装していますが、対応するサンプル曲が無いため検証は限定的です。
どちらも従来の曲でこれらの機能を使ったケースは確認できていません。

参照実装: `core/src/compiler/mod.rs`の`Compiler::apply_play_from`、
テストは`core/tests/golden.rs`の`play_from_*`/`play_to_*`。
